## 1. Bottom line

The user's model is directionally right: the BootROM exploit gives code
execution early enough to control the boot chain. But **code execution is not
persistence**. Each later stage verifies the next image, and the exploit must
either:

1. keep the signed bytes the verifier checks while running different bytes
   (magic/post-verification carrier, or pre-verification carrier), or
2. defeat the verifier itself.

On this tablet:

- **Custom system is already booting** under the tethered host unlock. The
  modified `vbmeta_b` flag and the custom `super` are in place; issue #235 is
  the same recipe. `[verified: log]`
- **Cold-boot persistence is still missing.** The corrected `magic64` carrier
  is the closest route: the old carrier was accepted by the stock SPL and
  reached the kernel; only its patch target was wrong. The corrected carrier
  changes that one target and is untested. `[verified: static/log]`
- Issue #106 adds a second, different route: patch **TOS** to disable AVB
  (`dis_avb`) and flash a patched boot/init_boot, without needing the ZTE
  unlock record. That is a **TOS/AVB bypass**, not a bootloader unlock. It is
  promising but depends on the BSP pre-verification bug and is `[unproven]` on
  this SPL build. An offline carrier has now been generated and structurally
  verified. `[verified: offline]`
- Issue #235 confirms a separate point: `verity 0` is flag 1
  (`HASHTREE_DISABLED`) only; Unisoc does not allow flag 2. BL unlock lets you
  replace `boot`/`vendor_boot`; `verity 0` lets you replace `super`. Both are
  needed for a custom system. `[verified: source]`

No device write was made for this report. The corrected `magic64` test and the
new TOS carrier test both remain gated on explicit user GO.

## 2. The W202DS bootchain, stage by stage

```
BootROM (SPRD3, on-chip)
  -> loads/verifies SPL (splloader)
  -> SPL/FDL1 (chipram) initializes DRAM, verifies TOS/SML and UBOOT/FDL2
  -> TOS/SML (secure world) provides VerifiedBoot/lock services
  -> UBOOT/LK: fastboot, AVB slot verify, dm-verity, kernel boot
  -> kernel/Android: vbmeta, system/vendor, Play Store
```

### 2.1 BootROM -> SPL

- The public primitive is CVE-2022-38694: a BootROM memory-corruption bug that
  lets a host execute a small unsigned payload in BootROM/FDL1 context.
  `[verified: source]`
- Our host flow uses that primitive to send `custom_exec_no_verify_65012f48.bin`
  and then a **patched SPL** (`spl-unlock.bin`) into RAM. The patched SPL NOPs
  four `signcheck` call groups, so it loads the modified LK. `[verified: source]`
- This is **RAM-only**. It does not make a cold BootROM accept an unsigned SPL
  image from eMMC. Erasing `splloader` and booting through the host is how the
  current tablet reaches Android. `[verified: device/log]`
- A persistent replacement SPL would need a BootROM-level bypass of SPL
  verification, or a signed-SPL vulnerability. We have neither. `[unproven]`

### 2.2 SPL/FDL1 -> TOS and UBOOT

- The stock SPL verifies the next images with the Unisoc BSP/DHTB scheme. DHTB
  has a SHA-256 field **and** a separate SIMGHDR certificate/signature; fixing
  only the SHA-256 is not enough. `[verified: static]`
- The B2¹² attempt failed exactly because it changed the LK payload and
  recomputed DHTB SHA-256 but left the original certificate. `[verified: device/log]`
- Two public carrier families exploit the verifier/loader parser differential:
  - **Post-verification** (`magic32`/`magic64`): the original signed payload is
    still what the verifier hashes; a jump prefix and runtime patch framework
    execute the patched code after verification.
  - **Pre-verification** (`bsp_sign_fxxker`): the original signed payload is
    moved to the footer's `payload_offset`; a modified payload is placed at the
    image start (`0x200`) where the loader executes.
  `[verified: source]`
- The **old magic64 carrier** was accepted by our stock SPL and reached the
  kernel. That proves the post-verification carrier path works on this device.
  It stayed locked/green because its patch target was the wrong runtime address.
  `[verified: device/log]`
- The **corrected magic64 carrier** targets `0xB50629B4`, the stock LK's
  `get_lock_status` entry, not `0x9F0629B4`. It is built and verified offline;
  only one byte differs from the old carrier. `[verified: static]`
- The earlier **pre-verification `uboot_b` carrier** did not produce a working
  boot (`r36`). That is a warning for any pre-verification route, but it does
  not by itself prove the SPL is patched; the geometry and target image differ.
  `[verified: device/log]`

### 2.3 TOS/SML

- TOS/SML is the secure-world side. It provides VerifiedBoot state and the
  `VerifiedBoot-UNLOCK`/HUK-derived token services. `[verified: static]`
- The `miscdata 0x2000` lock record route is gated by secure boot/LCS. On this
  unit the stock writer rejects unlock argument `1`, and `get_lock_status()`
  skips the record and erases `miscdata 0x2000` when secure boot is enabled.
  That route is dead here. `[verified: static/device]`
- The B2 LK stub only changes the **AP-side** lock verdict. It does not change
  secure-world state or make TOS attest as unlocked. `[verified: static]`
- Issue #106's `dis_avb` route is different: it patches a TOS verification
  function so the secure-world AVB check returns success. That can allow a
  patched boot image even when the AP lock record still says locked. It is not
  an unlock; it is an AVB bypass. `[verified: source]`

### 2.4 UBOOT/LK -> Android

- `get_lock_status()` at `0xB50629B4` is the single global AP-side lock verdict.
  r28 found two writers, eleven readers, and exactly one TEE query. A stub there
  changes `flash.locked` / `verifiedbootstate` for all AP consumers. `[verified: static]`
- The B2 LK stub makes LK report unlocked/orange. It does **not** by itself make
  dm-verity permissive. r35's host boot with stock `vbmeta_b` still reported
  `ro.boot.veritymode=enforcing`, yet `/system` was accepted; the failure was
  `/data`/`init_user0`, not a verity refusal. `[verified: log]`
- `verity 0` writes AVB flag 1 (`HASHTREE_DISABLED`) into `vbmeta`. That is what
  changes `ro.boot.veritymode` to `disabled` and lets the custom `super` mount.
  It is not an unlock and not a signature bypass. `[verified: static/log]`
- The current device has **both**: B2 LK unlock + modified `vbmeta_b` flag 1.
  That is why it reports `disabled` now, unlike r35's stock-vbmeta run.
  `[verified: log/backup]`

## 4. Issue #235 — what it actually establishes

Title: realme C53 UMS9230 bootloader unlocked with CVE-2022-38694.

- The user unlocked, flashed a custom ROM, and hit
  `avb_slot_verify() ... ERROR_PUBLIC_KEY_REJECTED` despite the log saying
  `LOCK FLAG IS : UNLOCK, SKIP VERIFY`.
- TomKing's answer: run `verity 0`; `disable-verity` is flag 1;
  `disable-verification` is flag 2; **Unisoc only allows flag 1**.
- He then states: `boot/vendor_boot` are controllable with BL unlock; `super`
  is controllable with disable-verity. `[verified: source]`

Implications for W202DS:

1. Unlock alone is not sufficient for arbitrary boot images. AVB can still
   return a key error for an unsigned/mismatched image.
2. Flag 1 is the supported way to let a modified `super` mount; it is already
   set on this tablet.
3. A custom kernel/ramdisk still needs either a bootloader unlock (B2/magic64)
   or an AVB bypass (TOS `dis_avb`). The two controls are distinct.

This is consistent with r35 vs the current device: `veritymode=disabled` is a
property of the modified `vbmeta`, not of the B2 unlock alone.

## 5. Issue #106 — what it actually establishes

Title: Support for ZTE Nubia Neo 2 T820 (UMS9620 family).

- The reporter tried `ums9620_test_dramtype2` and `ums9620_ZTE_universal`;
  `spl-unlock.bin` always failed at `EXEC FDL1` with `usb_send_failed(0/1)`.
- TomKing: the real unlock status is `miscdata 0x2000-0x2040`; if it is not
  empty but the system says locked, ZTE blocks the device.
- Later, TomKing says "actually we can root it": use `spd_dump_it`; in `FDL2>`
  type `dis_avb`; this is a **TOS-patch with a sign bypass**; "forget 38694".
- The tested command was:

  ```text
  spd_dump exec_addr 0x65012f48 fdl fdl1-dl.bin 0x65000800 \
    fdl fdl2-dl.bin 0xb4fffe00 exec dis_avb r init_boot r boot reset
  ```

  then patch `boot`/`init_boot`, then write them back. The reporter says
  "thank i succeeded". `[verified: source]`
- This is **not** a persistent bootloader unlock. It is a persistent TOS/AVB
  patch that lets a patched boot/init_boot run despite the ZTE lock record.
  It does not create an orange/unlocked fastboot state by itself.
- The platform is UMS9620/T820, not necessarily the same T760 variant as
  W202DS, and the ZTE build is different. It is strong evidence that the TOS
  route exists on a close cousin, not proof for this tablet. `[unproven]`

### 5.1 Offline `dis_avb` carrier for W202DS

We generated the carrier with the public `spd_dump_it` binary in **tool mode**
(no device connection):

```sh
spd_dump-main-x86_64-unknown-linux-musl -t \
  dis_avb_ex sml_b.bin trustos_b.bin exit
```

Inputs: stock slot-B `sml_b` and `trustos_b` from the 2026-10-17 full backup.
Output:

```
work/w202ds/tos-noavb/tos-noavb-bsp-bypassed.bin
sha256 0ef895a4177bf6ac53513fa64010c58992e88b886c1a408fb83a37f49f50fa13
size   5,237,528
```

The tool:

```
chsize bsp image: 0x22b18
detected mov at 0x770d4
detected mov at 0x78cc0
patch mov at 0x78cc0
```

The candidate is a pre-verification carrier:

```
0x000000  stock SML DHTB header, mImgSize = 0x4fe480
0x000200  patched TOS payload
0x4dc200  stock SML payload (verifier-visible)
0x4fe680  stock SML SIMGHDR footer, payload_offset = 0x4dc200
0x4fe6e0  stock SML certificate (0x438)
0x4feb18  end
```

The loader-visible TOS differs from stock by one word:

```
stock  TOS 0x78cc0: e0 03 14 2a   mov w0, w20
candidate 0x78cc0: 00 00 80 52   mov w0, #0
```

The verifier-visible SML payload/cert and the DHTB payload hash are unchanged.
`work/w202ds/tos-noavb/verify-tos-noavb.py` passes all 23 structural checks.
`[verified: offline]`

**Why it is not a result yet:** the candidate depends on the SPL/FDL1 BSP
pre-verification bug. If this W202DS SPL (2026-07-09 build) is patched, the
stock SPL will reject it before TOS runs. The earlier `uboot_b` pre-verification
carrier did not produce a working boot; that is a warning, not proof, because
the image geometry is different. `[unproven]`

Also, the current device is not in a valid test configuration for this route:
the flash `splloader` is erased, `uboot_b` is the B2 runtime-patch LK, and
`vbmeta_b` is already flag 1. A real `dis_avb` test would need a separately
reviewed write set (likely stock SPL + a bootable LK + patched `trustos_b`) and
a stock-TOS rollback. It cannot be improvised.

## 6. Route comparison

| route | what it changes | persistence | evidence on W202DS | main risk |
|---|---|---|---|---|
| **A. corrected magic64** | `uboot_b` carrier + stock `splloader` | cold boot, no host | old carrier accepted, reached kernel; corrected target untested | one-byte target / loader behavior; recover via BROM |
| **B. TOS `dis_avb`** | `trustos_b` carrier | cold boot, no unlock needed | UMS9620/T820 success in #106; W202DS carrier only offline | SPL may have BSP bug patched; TOS hang; test setup more complex |
| **C. record write** | `miscdata 0x2000` | not viable | secure-boot LCS gate; writer rejects `1` | dead on this unit |

Recommendation:

1. **Do not write yet.** The corrected magic64 carrier remains the first test
   because its transport/BSP acceptance is already demonstrated by the old
   carrier and only the target address was wrong.
2. When the tablet is reconnected and `fix-node.sh` is live, run the corrected
   magic64 test with explicit GO. It writes only `uboot_b` and stock
   `splloader`; the custom `super` and flag-1 `vbmeta_b` stay in place.
3. If it succeeds: verify `flash.locked=0`, `verifiedbootstate=orange`,
   `veritymode=disabled`, `sys.boot_completed=1`, then do a **second cold
   boot** with no host.
4. If it fails: recover B2 + host `spl-unlock`; do not immediately try the TOS
   carrier. Compare the failed boot's `uboot_log`/load behavior first.
5. Only if magic64 is ruled out should the TOS `dis_avb` route get a dedicated
   test design and GO. Its offline artifact is ready, but its SPL acceptance is
   the decisive unknown.
